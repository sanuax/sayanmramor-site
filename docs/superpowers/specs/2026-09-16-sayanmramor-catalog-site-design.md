# Дизайн: сайт-каталог sayanmramor (поддомен основного сайта)

Дата: 2026-09-16

## Контекст и цель

Новый, отдельный от `D:\calculator` проект в `D:\sayanmramor-site` —
сайт-каталог продукции sayanmramor, который позже станет поддоменом
основного сайта (связка с доменом — задача другого программиста,
вне рамок этого документа). `D:\calculator` (готовый калькулятор,
891 камень) не трогается и не переносится — новый сайт читает его
данные и переиспользует его JS-логику по ссылке, а не копированием.

Структура сайта:

- 9 отдельных страниц по типу изделия (Лестницы, Панно, Подоконники,
  Полы, Стены, Фасады, Столешницы в ванную, Столешницы на кухню,
  Ступени) — каждая с примерами работ (пока плейсхолдер, реальные
  фото пришлют позже) и урезанной версией калькулятора (материал +
  размеры + опции, без выбора типа изделия — он уже задан страницей).
- Раздел готовых изделий с фиксированной ценой (новая категория
  данных, которой владеет этот проект).
- Кнопка «Калькулятор», ведущая на существующий полный
  `sayanmramor-calculator.html`.

Фильтрации камня по типу изделия на урезанном калькуляторе **нет**:
показываются все 891 камня, как и в основном калькуляторе. Решение
подтверждено пользователем — реальных технических ограничений нет
(уже отражено в существующем `TODO` про кухонные столешницы в
`PRODUCTS`), тонкости обсуждаются индивидуально с менеджером при
нестандартном заказе. Не относится к делу, что раньше эта тема
обсуждалась — на практике жёстких правил не оказалось.

## Предварительный шаг, уже выполненный в `D:\calculator`

В процессе брейнсторминга обнаружилось, что для корректной работы
урезанного калькулятора новому сайту нужны не только `pricing.js`,
`material-picker.js` и `data/slabs.json` (уже переиспользуемые по
ссылке), но и конфигурация ценообразования, которая раньше была
зашита только в `sayanmramor-calculator.html`: `PRODUCTS` (9
категорий с `label`/`complexityMultiplier`/`type`), `SAW_MARGIN_CM`,
`AREA_WASTE_FACTOR`, `WORK_MULTIPLIER`, `HARDNESS_WORK_MULTIPLIER`,
`OPTION_SURCHARGE`. Без этого урезанный калькулятор либо дублировал
бы эти цифры (риск рассинхрона), либо не смог бы вызвать
`Pricing.calculatePrice` с теми же параметрами.

По решению пользователя это вынесено в новый файл
`D:\calculator\product-types.js` (тот же UMD-паттерн, что у
`pricing.js`/`material-picker.js`), а `sayanmramor-calculator.html`
подключает его через `<script src="product-types.js">` и
деструктурирует константы из `ProductTypes` вместо локального
объявления. Изменение проверено: `node --test tests/pricing.test.js
tests/material-picker.test.js` — 57/57 тестов проходят как до, так и
после правки; отдельно поднят `python -m http.server` и подтверждено,
что `product-types.js` отдаётся и содержит все 6 ключей с 9
категориями. Изменение сделано, но не закоммичено в `D:\calculator`
— оставлено на усмотрение пользователя.

## Технический подход

Статический сайт: чистый HTML/CSS/JS, без сборки и без фреймворка —
как и существующий калькулятор. Никакого Node/build на проде не
нужно, легко передать под любой хостинг.

### Правило "не дублировать"

- **Данные и логика движка** — `data/slabs.json`, `data/images/`,
  `pricing.js`, `material-picker.js`, `product-types.js` —
  подключаются по ссылке на `D:\calculator`, не копируются. Один
  источник правды для камня, формулы цены и списка типов изделий.
- **Контент нового сайта** — 9 HTML-страниц категорий, раздел готовых
  изделий, примеры работ — полностью принадлежит `sayanmramor-site` и
  дублирования не требует: у каждой из 9 страниц просто один вызов
  общего JS-модуля с ключом своей категории (см. ниже), а не
  скопированная логика.

### Локальная разработка

`fetch()` не работает через `file://`, поэтому и сегодня, при работе
с одним калькулятором, разработка ведётся через
`python -m http.server`. Так как новому сайту нужен доступ к
`D:\calculator` (соседняя папка), локальный сервер во время
разработки запускается из `D:\` (родитель обеих папок):

```
cd D:\ && python -m http.server 8000
```

Тогда пути вида `/calculator/data/slabs.json`,
`/calculator/pricing.js`, `/sayanmramor-site/categories/poly.html`
работают из коробки, без symlink'ов и второго сервера. Топология на
проде (общий хостинг/файловая система или нет) намеренно не
фиксируется в этом документе — по решению пользователя, это решается
позже вместе с программистом, который будет связывать поддомен с
основным сайтом; относительные пути `../calculator/...`, заложенные
здесь, — рабочее предположение для этого момента, а не гарантия для
прода.

## Урезанный калькулятор на странице категории

Каждая страница категории фиксирует тип изделия атрибутом контейнера:

```html
<div id="calc" data-product-key="pol"></div>
...
<script src="../../calculator/pricing.js"></script>
<script src="../../calculator/material-picker.js"></script>
<script src="../../calculator/product-types.js"></script>
<script src="../js/category-calculator.js"></script>
<script>
  CategoryCalculator.init(document.getElementById('calc'), 'pol');
</script>
```

`js/category-calculator.js` (один общий модуль, без per-страничной
логики):

1. `fetch('.../calculator/data/slabs.json')`, показывает состояние
   загрузки/ошибки (как в полном калькуляторе).
2. Инжектит разметку модалки пикера материала (оверлей, поиск, чипы,
   сетка, лайтбокс) через JS — не копирует HTML пикера в 9 файлов;
   вызывает `MaterialPicker.init({ stones: data.stones, onSelect })`.
3. Поля: материал (через пикер, все 891 камень, без фильтра — решение
   подтверждено), ширина, длина, три чекбокса опций (сложная форма /
   полировка / монтаж, те же ставки из `OPTION_SURCHARGE`). Выбора
   типа изделия нет — берётся из `data-product-key`.
4. На изменение любого поля вызывает `Pricing.calculatePrice({...})`
   с `product = ProductTypes.PRODUCTS[productKey]` — **тот же вызов
   и та же функция**, что использует основной калькулятор, поэтому
   поведение (тип A/B, лестница-предупреждение, "нет подходящего
   слэба", остаток и т.д.) идентично без переписывания.

Кнопка «Калькулятор» на каждой странице и в общей шапке — обычная
ссылка на `../../calculator/sayanmramor-calculator.html` (или
финальный путь, который определит программист интеграции).

## Готовые изделия (`data/products.json`)

Универсальный формат, рассчитанный и на ручную правку текстом, и на
будущую простую форму (способ редактирования пользователь уточнит
позже, когда определится с ценами/описаниями/материалом для первых
товаров — светильников, эксклюзивных столов, ракушек):

```json
{
  "updated_at": "2026-09-16T00:00:00+03:00",
  "products": [
    {
      "id": "svetilnik-01",
      "name": "Светильник из оникса",
      "category": "svetilniki",
      "price_rub": 45000,
      "description": "Ручная работа, подсветка в комплекте.",
      "photos": ["assets/products/svetilnik-01/1.jpg"],
      "available": true
    }
  ]
}
```

- `category` — свободная строка, не завязана на 9 категорий
  калькулятора; новые категории готовых изделий добавляются без
  правки кода.
- `price_rub` и `description` допускают `null` — для товаров, у
  которых цена/описание ещё не уточнены; `catalog.js` в этом случае
  рендерит карточку с пометкой «цена по запросу», не падает.
- `available: false` — товар не в наличии (точное поведение — скрыть
  или пометить — решается на этапе реализации, малозначимая деталь).
- Фото — файлы в `assets/products/<id>/`, пути перечислены в массиве.

`js/catalog.js` на `katalog.html` рендерит сетку карточек из этого
файла — аналогично тому, как `material-picker.js` рендерит сетку
камней, но без фильтров/поиска (не требовались в этом обсуждении;
можно добавить отдельной задачей, если понадобится при реальном
объёме товаров).

## Тестирование

- Переиспользуемая логика (`Pricing.calculatePrice`,
  `MaterialPicker.*`) уже покрыта существующими тестами в
  `D:\calculator\tests\` — не дублируется здесь.
- `js/category-calculator.js` — по возможности чистая часть (сборка
  параметров для `Pricing.calculatePrice` из полей формы) выносится в
  тестируемые функции по аналогии с `pricing.js`; DOM-обвязка
  проверяется вручную в браузере, как и в существующем калькуляторе.
- `js/catalog.js` — рендер карточек из `products.json`, включая
  случаи `price_rub: null` и `available: false`, проверяется вручную
  в браузере (нет DOM-тест-раннера в проекте, как и в calculator).
- Ручная проверка (через `python -m http.server` из `D:\`): каждая из
  9 страниц категории — пикер открывается, расчёт совпадает с тем же
  расчётом в полном калькуляторе для тех же параметров; переход по
  кнопке «Калькулятор»; каталог готовых изделий рендерится, включая
  товары без цены.

## Известные ограничения / вне рамок

- Точная топология деплоя (общий сервер с calculator или нет, как
  поддомен физически получает доступ к `data/slabs.json` в проде) —
  сознательно не фиксируется, решается вместе с программистом
  интеграции.
- Способ редактирования `products.json` (вручную текстом или через
  простую форму) — открытый вопрос, пользователь уточнит после
  получения реальных цен/описаний первых товаров.
- Точный визуальный дизайн (вёрстка, типографика, фирменный стиль) —
  отдельный проход с навыком `frontend-design` на этапе реализации,
  не фиксируется в этом документе.
- Изменение в `D:\calculator\product-types.js` /
  `sayanmramor-calculator.html` сделано, но не закоммичено — коммит
  делается пользователем или по отдельному запросу.
